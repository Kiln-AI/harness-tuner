# Memory

Memory is for **knowledge that outlives sessions**: problems worth solving, things tried and learned, facts about this project's world. It is NOT for working state — your context window (and session resume) holds the state of *this* session; if a thing matters only until you finish, it doesn't belong here.

The discipline (Anthropic memory-tool shape): **check memory first, record as you go, assume interruption.** A finding that lives only in context dies at compaction. Write at the moment of learning, never in an end-of-session batch.

## The API — six REST endpoints on the running Kiln app

**In a Kiln Harness Tuner agent session** there is no generic Kiln REST tool: use the gateway's memory operations — `memory_list`, `memory_get`, `memory_summary`, `memory_create`, `memory_update` (the `kiln-harness-tuner-gateway` skill) — which apply the scopes and conventions below for you; the endpoint table is for other sessions. Elsewhere, no dedicated memory tool or server exists: call the endpoints with the generic Kiln REST tool you drive Kiln with (`call_kiln_api` or this session's equivalent) — that's what makes these conventions portable between Claude Code and the Kiln assistant. Records live in the Kiln project's `assistant_memory/` folder (human-readable `.kiln` files, concurrent-append safe) — reach them through the API only; in a Kiln Harness Tuner session the project tree is not readable. `{project_id}` = the Kiln project's id.

Each row links to that endpoint's full reference — parameters, body fields, response shape — in the generated `kiln-api` skill. One `Read`, no catalog hop. Those links are **Claude-Code-side**: they resolve against this repo's `.claude/skills/` layout, which the Kiln assistant does not have. The endpoints and conventions in the table are the portable part; drop or repoint the links if this file is ever promoted into a Kiln skill tree.

| Operation | Call |
|---|---|
| save | [`POST /api/projects/{project_id}/memories`](../kiln-api/references/api_docs/post_api_projects_project_id_memories.md) — body: `overview` (req, ≤280), `scope` (req — no default), `content?` (≤4000), `tags?` |
| list | [`GET /api/projects/{project_id}/memories?scope=…&tags=…&tags=…&content_match=<regex>&limit=50&offset=0`](../kiln-api/references/api_docs/get_api_projects_project_id_memories.md) — repeat `tags` = AND; newest-first; truncation nudge includes tag counts |
| summary | [`GET /api/projects/{project_id}/memories/summary?scope=…`](../kiln-api/references/api_docs/get_api_projects_project_id_memories_summary.md) — omit scope for all scopes; counts + tag cardinalities + newest, no content |
| get | [`GET /api/projects/{project_id}/memories/by_ids?ids=…&ids=…`](../kiln-api/references/api_docs/get_api_projects_project_id_memories_by_ids.md) — full records; unknown ids omitted |
| update | [`PATCH /api/projects/{project_id}/memories/{memory_id}`](../kiln-api/references/api_docs/patch_api_projects_project_id_memories_memory_id.md) — partial: omitted fields untouched; explicit null clears `content`; last-writer-wins |
| delete | [`DELETE /api/projects/{project_id}/memories/{memory_id}`](../kiln-api/references/api_docs/delete_api_projects_project_id_memories_memory_id.md) — hard delete, confirmed junk only |

**Scopes** (explicit on every call, no defaults): `"project"` = project-wide knowledge (constraints, lessons); `"task::<task_id>"` = work on that task (issues, experiments, hypotheses, dead ends). Scope is an opaque exact-match string — a convention, not a reference. ⚠️ **A list or search with no `scope` returns every scope**, so an agent on one task can read another task's experiments and lessons. Inside Kiln Harness Tuner sessions the gateway refuses any memory list, search or write that does not name `project` or the run's own `task::<id>`; outside Kiln Harness Tuner, pass the scope yourself, every time.

## Orientation (session start, before assuming anything is unknown)

1. `summary` — counts by scope/tag = the shape of what's known. Empty ⇒ first session: seed `constraint` memories from the project's brief.
2. Project scope: list `constraint`, then `lesson`.
3. Task scope: read the singleton `baseline` record (`tags=baseline` — the authoritative current-baseline pointer: the rc id is the `rc_<id>` tag, and content is the promotion chain; ⚠️ Kiln Harness Tuner train-side loop agents skip this read — the orchestrator hands you the rc id; see the `baseline` row), and, when you need the numbers behind those promotions, the `val` record (`tags=val` — ⛔ never on a train-side lane; see the `val` row); then list `issue` (read `p0`/`p1` first), `dead_end` (before forming any plan), `hypothesis`, then recent `experiment` overviews (the accepted merge's experiment also names the baseline — kept as redundancy; the `baseline` record is what you trust).
4. Memories with `content_length: 0` are consumed from the listing alone — don't fetch. Fetch the rest by id, in batches, only where the overview says you need the body.

## Write discipline

- **One finding per memory.** The caps (280/4000) are the discipline — and both are **API-enforced at write time**, not advisory: the server answers 422 (`string_too_long`) to any POST/PATCH past overview 280 or content 4000. If it doesn't fit, it's almost always several findings — split it. A genuinely long-form artifact (analysis doc, comparison) is a workspace file, cited by path from a memory — noting workspace files don't outlive the project.
- **`overview` is a load-decision signal, not a title.** Front-load the verdict/number so a future reader can decide without fetching: `"EXP 0715-w3-1 (prompt): no-refetch rule — accuracy: +12pp, base=64, cand=76, n=40, p=.01"`, never `"Experiment 7 results"`. If the overview says everything, leave `content` null. (Inside the Kiln Harness Tuner loop the measurement row after the ` — ` has an exact frozen shape with **one owner** — the "Frozen format" block in `kiln-harness-tuner-experiment-analysis`. Examples here illustrate front-loading, never that format; go read it rather than copying one of these.)
- **Content = observation + conditions + evidence.** "Batch API 429'd at 50rps on 07-04 (n=2 runs, staging)" — never universal rules, never platitudes. State evidence level and source (human-stated vs inferred, n, what wasn't controlled) as prose. Cite Kiln records as prose ids ("run_config 424242901234").
- **Check before writing:** list the relevant tag first — if a memory on this finding exists, update it, don't duplicate.
- **Corrections = update the memory** with the new understanding, appending a one-line correction note in content ("corrected 07-14: was attributed to prompt rule, actually the judge swap"). Newer wins; keep history honest inside the record. Delete only confirmed junk — a *ruled-out approach* is not junk, it's a `dead_end`.
- **Negative platform claims are BLOCKED — never stored.** "X doesn't work / isn't stored / is ignored / the API drops Y" is almost always temporary (a bug, an outage, a stale build, a wrong diagnosis) and unfit for forever-memory — do not store it at all, not even hedged as a `lesson`. The one adjacent allowed form is **mitigation-shaped and probe-confirmed**: "if X is flaky, try Y to mitigate" — stored only after you actually probed that Y works, citing the probe, and still used sparingly (temp information in permanent storage). Example — blocked: "memory PATCH drops the content field"; allowed (after a probe): "if a memory PATCH seems to drop content, re-send with an explicit content key — probed 07-30, second write landed".
- **If a memory write fails, disclose it in your return** — record the failure and the intended content in the prose field your role hands back (`findings` / `build_notes` / `rejected_summary` / your report), so the finding survives in the run record even though the store never got it. Do not memory-store the failure itself (that would be a negative platform claim — see above); retry the write, and if it keeps failing the disclosure is the record. A disclosure rides **once** — the return where the failure happened — as a summary (the finding's gist + what the full content was for), not the verbatim 4,000-char body, and it is **exempt from any length budget on that field** (e.g. the planner's ~1,200-char `rejected_summary` budget); later waves never re-carry it.
- **Not memory-worthy:** session working state (context/resume covers it) · per-trace annotations (Kiln feedback model, child of the trace) · why-an-artifact-was-created (its frozen `provenance`, written once at creation) · generalizable craft that is true beyond this project (put it in a skill instead) · anything restating what an artifact/eval already records.

## Tags — seed vocabulary (8 + priorities)

> **Code reference.** Inside the Kiln Harness Tuner loop, every convention in this section and the two below — the kind tags, the issue prefixes, the experiment suffixes, the `key: value` content lines code reads back, the issue head and tail layout, the five open-unknown lines — is typed in `src/kiln_harness_tuner/memory_schema.py` (`RecordKind`, `IssueState`, `ExperimentState`, one view per kind). That module is the authoritative list of what CODE reads from a record; this skill stays the authoritative guide for what an AGENT writes and reads. Keep the two in step: a new prefix, suffix or code-read line lands in both.

Free-form beyond this seed, snake_case, never a closed enum. Governance: if real usage keeps awkwardly cramming a recurring kind of finding into these eight, that observed usage is the evidence for adding a tag — extend by evidence, not speculation. (`baseline` earned its row this way: the singleton needs a direct query key — orientation fetches it by tag, no list-and-scan. `val` earned its own by being an **access class** rather than a topic: the boundary between train-visible state and val metrics has to be queryable, and a substring of an overview is not.)

Two shapes appear here beyond the plain topic tag. **Faceted tags** carry an id — `eval_<eval_id>` on an `issue`, `rc_<rc_id>` on the `baseline` record: they are the structured slot a memory record otherwise lacks, and code reads ids from them rather than parsing prose. **Access-class tags** — today just `val` — mark what a record may not be shown to; see the `val` row.

| Tag | What it is | Write when | Query when |
|---|---|---|---|
| `issue` | A problem worth solving — needs no solution idea to be recorded. Includes problems blocked on a human (state what's needed from whom in content). **An eval-derived issue is a derived child of that eval**, bound by an `eval_<eval_id>` tag; an issue filed before any eval measures it is bound later, when one is built — see "Issues are derived children of evals" below. **Lifecycle = overview prefixes, update-based — no state tags**: open is the default (a priority tag, nothing more); `"UNMEASURED: "` = seeded from an eval but nobody has checked yet whether the baseline actually fails it (setup seeds every active eval one; measuring it is the planner's spend decision); `"UNMEASURABLE: "` = the eval it binds to is gone or has left the active set, so it cannot be experimented on at all — a status, never a decision and never a close (the finding may still be true; the cause line says which); a landed fix front-loads `"FIXED: "` onto the overview + a content one-liner citing it (`"fixed 07-15 by rc_207, EXP 0715-w3-1"`); `"WONT_FIX: "` = deliberate decision or not reproduced, reason in content (cite which); reopened = strip the prefix + append the provenance line (`"- reopened when promoting baseline rc_213. Issue repros on rc_213."`) — never a duplicate memory. One prefix at a time: setting a new one strips the old — but **never out of a terminal state**: `FIXED:`/`WONT_FIX:` are the loop's own decisions and it does not un-close them (a human re-opens by stripping the prefix and appending the provenance line). The Kiln Harness Tuner writers refuse rather than overwrite. Priority tags are **never removed**, even on close — the severity record stays, and priority is **source-owned** (from `spec.priority` where a Spec exists), so a re-sync replaces the tag rather than an agent re-prioritizing. | Trace analysis finds a failure mode; the user reports a problem in chat; an iteration fixes X but regresses Y (keep the config, file the regression). One eval's issues: `tags=issue&tags=eval_<eval_id>`. Round end: surface human-blocked issues. |
| `hypothesis` | A candidate change/approach not yet run — including ideas for later. Cite the issue ids it addresses in content. | An idea forms that you aren't acting on right now. | Choosing the next experiment; before inventing a plan that may already exist. |
| `experiment` | One thing tried + outcome — any size, from full eval-gated runs to quick n=3 checks (state evidence level; small n gives direction, never validation). Opened before running (hypothesis + prediction), updated with the verdict; updatable forever as interpretation evolves. Content fields: hypothesis / lever / run_config ids (inside the Kiln Harness Tuner loop code appends `rc: <id>` and `change: <summary>` the moment the build lands, and `reused rc: <id>` when the arm measures a prior run's build) / what it cost — inside the Kiln Harness Tuner loop that slot is `bundle cost` (the loop's one spend figure for an experiment — that label, never a bare "spend"; defined in `kiln-harness-tuner-experiment-analysis`), and `spend` everywhere else (a hand-run n=3 check has no bundle) / result / verdict + why / next. **Overview state suffixes** (lifecycle vocabulary — read them, and write them when you open experiments): opened as `"EXP 0723-w4-2 (prompt): <short hypothesis> — RUNNING"`; the verdict *replaces* the suffix with front-loaded numbers (`"… — accuracy: +18pp, base=62, cand=80, n=34, p=.04"` — inside the Kiln Harness Tuner loop that row's shape is frozen in `kiln-harness-tuner-experiment-analysis`, which owns it; elsewhere, any labelled numbers); `— FAILED (infra: <error_class>)` = killed by infra, neither win nor dead end, retryable; `— ABANDONED (<why>)` = aborted mid-run (tripwire, orchestrator restart), no verdict; `— NOT LANDED (<detail>)` = a stop rule of the measurement engine ended the arm before its train split was judged in full, so the rest was not paid for: `(<k>/<n> targets fixed)` when a named `target_items` item still failed; `(<k>/<n> fixed, <b>/<g> guards broke)` from the discriminating block (the parent's failures and a few passes, judged first), with `residual gate:`, `residual still failing:` and `residual guards broke:` content lines naming the items per eval; `(stopped at n=<n> by <rule>: <numbers>)` for any other rule (clearly worse quality, futility, invalid output, not faster or cheaper) — the lever is untested, not disproven (a different build for the same targets is fair game; the same rc is not); `— CAPPED (capped at $<x> after <n> items: inconclusive — net +<a>/−<b> so far)` = the measurement reached the arm's spending cap: inconclusive, never a dead end or a failure — the rows are kept and a later arm on the same rc with a larger cap goes on from them; `— PROMOTED <date>` appended when the experiment's rc becomes the baseline; `— HELD (constraint <id>) <date>` appended when the val gate escalated on that OPEN constraint instead of judging the numbers (the rc is resubmitted unchanged once the constraint is answered); `— REJECTED AT VAL <date>` appended when a val gate compared the experiment's rc and passed it over (never removed — the rc is never re-submitted unchanged, though it stays eligible as a merge ingredient; the same design re-enters as a new experiment). | You are about to run something with a predicted effect; again at verdict. | "What's been tried?"; merge-eligible wins = verdicts since the last promotion without `— PROMOTED` (a `— REJECTED AT VAL` one is an ingredient only — never re-submitted unchanged); a `— RUNNING` overview from a dead run means abandoned work, not a result. |
| `dead_end` | An approach ruled out — don't retry (with the conditions under which it's dead, citing the experiment id). | A lever is exhausted or an approach refuted. | BEFORE forming hypotheses — this is the map that stops re-exploration. |
| `constraint` | A requirement, preference, or committed decision binding our work — from the task owner ("OpenAI models only"), the world, or our own choices ("optimize cost before quality — agreed 07-04"). Source, hardness, and rationale in content. **Open unknowns are `constraint` memories with an `"OPEN: "` overview prefix** — `"OPEN: unknown if API docs exist for the graphql endpoint"`; content: the verbatim question, the default assumed, source (`human` vs `assumption` — assumptions promote on confirmation), and a re-ask condition as prose ("re-ask when the API fix ships"). Answered = update in place: strip the prefix, append answer + source + date — never a duplicate. | Someone states a requirement; a binding choice is made; a question arises mid-work that can't be asked now — apply a default, record the `OPEN:` unknown, keep working. | Session start, and before designing any candidate. Kickoff/frontload: `OPEN:` records first — they are pre-generated question candidates; never ask what's already answered. |
| `lesson` | Something learned about this project's world or how to work in it effectively: API/data/infra behavior and quirks, effective procedures ("judge batches >200 items flake — chunk to 100"). Concrete observations only. | You learn something the next session would otherwise rediscover the hard way. | Session start (project scope); before touching the part of the world it describes. |
| `baseline` | **The singleton task-scope record naming the current baseline run-config** — the authoritative pointer session startup reads. Singleton by convention: PATCHed at every promotion, never duplicated. **The rc id is a faceted tag, `rc_<rc_id>`** — for run config `424242035642` the tags are `["baseline", "rc_424242035642"]` (the prefix is added to the id, never to an already-prefixed name). Read the id from there, never from prose. Overview: free prose, **no format contract**, anyone may rewrite it (`"Baseline: run config 424242035642 — promoted 07-15 by EXP 0715-w3-1"`); content: the promotion chain — **one rc id per line, newest first**, nothing else on the line required — deliberately dumb, because a bad parse costs a cache screen and nothing more. **It carries NO val metrics**: those numbers live in `val`, so the split boundary is a record rather than a substring of an overview. | **Created** on a cold task by the Kiln Harness Tuner setup phase's pre-flight step (the task's `default_run_config_id` if it has one, else the most recently created rc, with the rule named in the record's provenance; zero run configs is an instructive fatal, never a sentinel baseline). After that only the promotion apply step updates it — moving the `rc_` tag, prepending the winner to the chain (in the Kiln Harness Tuner loop both writers are orchestrator code; the loop never sets the human-facing `default` rc flag, and a newer user-set default never moves an existing baseline on its own). | Orientation: fetch directly via `tags=baseline`. ⚠️ Kiln Harness Tuner train-side loop agents (batch planner, rc-build, analyzer, eval-build) **never read it** — the orchestrator hands them the rc id, so the read buys nothing, and it sits beside the `val` record in the same task scope. |
| `val` | **The singleton task-scope validation-stats record** — the val summary of every baseline promotion. `val` is an **access class**, not the record's name: the rule it exists to support is "the train lane never fetches `tags=val`", and it generalizes to any future val-grade record. Overview: generic and **numberless** (`"Validation metrics for each baseline promotion (val-grade; the numbers are in content, never here)"`), so a listing is safe to fetch even when the content is not; content: one line per promotion, newest first — `"rc_213 (07-16, EXP 0716-w4-2) ← rc_207 — +9% mean win rate vs rc_207"`. Summary numbers only, **never item/trace-level val detail**. This is the **only** memory allowed to carry val-split metrics (Kiln Harness Tuner split guarantees). | Written by the promotion apply step, right after the `baseline` write — created at the first promotion, so a freshly seeded task has a `baseline` record and no `val` one. A failed write here is logged and skipped: it is reporting, and a promotion must not fail on it. | The promotion agent, the report writer at exit, and human/interactive orientation. ⛔ **Never on a train-side lane** — this record IS val metrics, so a read is the leak the split guarantees exist to prevent. |

**Screening records (Kiln Harness Tuner).** Code records every screened candidate's result in task scope with the `screen` tag, so a later run starts from it. A survivor is a `lesson` with the overview `SCREEN SURVIVOR: <label> — <passed>/<judged> vs baseline <b>` (under speed and cost: `SCREEN SURVIVOR: <label> — lost <k> of <n> baseline passes, no loss rate above <X>% at 95%`, and its `quality` line names the fixes of baseline failures apart as noise level; read it as a bound on a loss, never as "quality held"); a dead end is a `dead_end` with the overview `SCREEN DEAD END: <label> — <reason>`. The content is `key: value` lines, in this order: `candidate`, `run config`, `label`, `overrides` (JSON), `parent rc`, `round` (the size tier), `round no` (the run's round counter), `items`, `screened on evals`, `verdict`, `reason`, `quality` (`passed <p>/<n> vs baseline <b> (fixed <f>, broke <k>)`), `measured` (the full measured line), `run` (the run id), `date`, `baseline rc`, `result` (the result as one JSON line, which code reads back). Quality is against that run's baseline; latency is from that run's window and is orientation only in a later run. Agents read these records and never write them. Older dead-end records may have the first six lines only (`candidate`, `run config`, `round`, `screened on evals`, `reason`, `measured`), and code still reads them.

**Generality lines (Kiln Harness Tuner).** An experiment record may carry a code-written `generality:` line: what the leak check between build and measurement found in the prompt or the skills, or why it could not check.

**Reference-check lines (Kiln Harness Tuner).** An experiment record may carry a code-written `reference check:` line: a skill or tool name that the build's prompt or skills use and the run config does not attach. A failure on the cases that use that name can be the build's breakage, not the lever.

**Priorities** — composable tags, primarily on `issue`; re-prioritize via update, never a duplicate memory:

- `p0` — blocks the project goal or causes user-visible harm; work it now.
- `p1` — material win on the agreed metrics (quality/cost/latency); the default queue.
- `p2` — real but minor; picked up when nothing above it remains.
- `p3` — tracked so it isn't lost (often: someone asked us to note it); no intent to work it in this project — revisit only if asked or it becomes trivial in passing.

**Who writes lifecycle state (Kiln Harness Tuner loop runs):** the format-critical writes above — the `baseline` and `val` records, `FIXED:`/`WONT_FIX:`/reopen prefixes, `OPEN:` records, experiment open/verdict/state suffixes — are performed by the orchestrator **code** from structured agent returns (the formats are frozen in code, in `src/kiln_harness_tuner/memory_schema.py`); loop agents make discovery writes only (`lesson` / `dead_end` / new `issue`, at the moment of learning). The Kiln Harness Tuner **setup phase** (a pre-flight step of the same code) owns the derived-child writes: seeding the `baseline` record on a cold task, seeding and re-syncing eval-derived `issue` records, the `eval_<id>` binding tag, `UNMEASURABLE:` flags, and — from a `measure_issue_baseline` batch item — clearing `UNMEASURED:` or setting `WONT_FIX:`. In interactive sessions there is no orchestrator — follow the same formats by hand.

## Issues are derived children of evals

**The eval is the parent.** Not the Spec: not every eval has one, and where a Spec does exist it is optional enrichment (usually the best human-authored description), never the key. An `issue` memory is the *derived child* — the planner-readable statement of the problem an eval measures — so the two never drift into independently-edited twins.

- **Binding = the tag `eval_<eval_id>`** (e.g. `eval_424242966189`) — snake_case, no separator characters. Not the content line: `- eval: <id> (built <date>, reproduced)` stays as the human-readable record, but the tag is what machines read. Both directions are one call: *does this eval have an issue?* → `tags=issue&tags=eval_<id>`; *do all evals have issues?* → one `tags=issue` listing, set-difference the binding tags against the eval list.
- **Cardinality is one eval → N issues.** Setup seeds one per active eval; the loop adds more as it discovers sub-mechanisms of the same criterion. An issue MAY carry several bindings (a problem found on eval X that later gets a purpose-built narrower eval Y) — it is only `UNMEASURABLE:` when *none* of its bindings is active.
- **An issue must *end up* bound** — tag it when an eval already measures it; when none does, the loop's `eval_only` item binds it via `link_eval` once one is built. An issue that is unbound with no eval pending is a bug: setup repairs the mechanical cases (exactly one eval id in the content, and that eval exists) and reports the rest. It never guesses a binding.
- **Content has two owners, split by one delimiter line** — `— setup wrote everything above; lines below belong to the loop —`. Above it: the description, eval identity, priority and its source, and a `status: … fp: … synced …` line (a sync-time snapshot; the overview prefix is the authoritative state). Setup replaces that whole block when the eval's rubric, config, spec or priority changes. The delimiter and everything below are loop-owned and append-only: setup preserves them byte-for-byte and never parses them for meaning. **Never edit above the delimiter by hand** — the next sync overwrites it; findings and history go below.
- A record with **no delimiter** (legacy, or written by an agent) is treated as entirely loop-owned: setup prepends its head and touches nothing else.

## Division of labor with artifact provenance (never write the same fact twice)

Facts about one artifact, known at its creation (why it exists, what it derives from, whose judgment) → the artifact's `provenance`, stamped at creation, **immutable, written once**. Everything that *evolves* or spans artifacts → memory. The pipeline: an `experiment` memory records the trial and its evolving interpretation → `dead_end`/`lesson` distill what it taught → `constraint` records what we committed to because of it. Memories cite artifact ids as prose; artifacts never point at memories.
