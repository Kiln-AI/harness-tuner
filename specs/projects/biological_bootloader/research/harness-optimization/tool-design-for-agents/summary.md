# Tool design for agents

Researched 2026-11-10. Sources are mostly from the last 12 months; older ones are marked.

## Bottom Line

The field agrees with the overview's central claim (6.3): a good software API is usually a poor agent tool, and the fix is a curated layer designed from the agent's workflows, not a 1:1 endpoint mirror. Anthropic, OpenAI, Block, GitHub, Microsoft and FastMCP all say this, and GitHub, Copilot, Block, OpenAI and Vercel report gains from *fewer* and *merged* tools. The strongest measured levers are: cap and shape tool results; move aggregation and call chains out of the LLM loop (wrappers or code execution); cut tool count and overlap; and write descriptions, parameters and errors for the model. Two overview statements need softening. Tool search is not "almost always" worse: it beats loading a large catalog by a wide margin, although it has real failure modes and no study compares it with a tool-listing skill. And code execution is not a universal win: it wins on data-heavy and chained tasks, ties or loses on small clean tool sets, and hurts some model families.

## Key Findings

- **Endpoint mirrors are the root smell** — "tools that merely wrap existing software functionality or API endpoints" are "a common error" ([Anthropic, 2025-09-11](https://www.anthropic.com/engineering/writing-tools-for-agents)); "Bootstrap, Don't Deploy" OpenAPI conversions ([Lowin, 2025-07](https://jlowin.dev/blog/stop-converting-rest-apis-to-mcp)); "Outcomes, Not Operations" ([Schmid, 2026-01](https://www.philschmid.de/mcp-best-practices)). Confirms overview 6.3.
- **Consolidate chains; mine traces for them** — Anthropic: tracking tool calls "can help reveal common workflows … to consolidate"; its `get_customer_context` example is the overview's `get_user_data` roll-up. Block's Linear server went from 30+ tools to 2 ([Block](https://engineering.block.xyz/blog/blocks-playbook-for-designing-mcp-servers)). Two styles: a workflow roll-up removes round trips; `method`-enum multiplexing (GitHub) only removes definitions.
- **Tool count and overlap cost accuracy** — Copilot lost 2–5 pp with ~40 tools against 13 ([GitHub, 2025-11](https://github.blog/ai-and-ml/github-copilot/how-were-making-github-copilot-smarter-with-fewer-tools/)); OpenAI's soft limit is "fewer than 20" ([OpenAI](https://developers.openai.com/api/docs/guides/function-calling)); a 584-tool production catalog lost 16–23 pp F1, with a 10 pp "confusion gap" even under perfect retrieval ([arXiv 2606.17519](https://arxiv.org/html/2606.17519)). The overview has no "too many or overlapping tools" smell; it should.
- **Removing tools is a lever** — Vercel's d0 went from 18 tools to bash + SQL on Opus 4.5: 80% → 100% success, 3.5× faster, 37% fewer tokens (5 queries only; it needed a well-documented semantic layer) ([Vercel, 2025-12](https://vercel.com/blog/we-removed-80-percent-of-our-agents-tools)). Missing from the overview.
- **Published size thresholds** — Claude Code warns at 10,000 tokens per MCP result, caps at 25,000, and saves text over 50,000 characters to a file ([docs](https://code.claude.com/docs/en/mcp)). In the wild, one tool averaged 557,766 tokens per call ([Microsoft Research, 2025-09](https://www.microsoft.com/en-us/research/blog/tool-space-interference-in-the-mcp-era-designing-for-agent-compatibility-at-scale/)). Confirms the overview's first smell and its "blocks everything" rank.
- **Shape results for the model** — drop UUIDs and noise fields; resolving ids to readable names "significantly improves" precision; a `concise`/`detailed` enum cut a result to about a third (Anthropic). Return handles (MCP `resource_link`, file paths) for long documents. Format (JSON/YAML/TOON/Markdown) has a small effect that depends on the model; 2026 benchmarks disagree ([arXiv 2605.29676](https://arxiv.org/html/2605.29676v2)).
- **Errors are prompts** — MCP 2025-11-25 puts input-validation errors in the tool result (`isError: true`) so models can self-correct ([spec](https://modelcontextprotocol.io/specification/2025-11-25/server/tools)). Microsoft found 3,536 of 5,983 "successful" results were really errors. Missing from the overview as a lever.
- **Descriptions help on average but are not free** — 97.1% of 856 public MCP tool descriptions have a smell; fixing them gave +5.85 pp task success, but +67% steps and regressions in 1 case in 6 ([arXiv 2602.14878](https://arxiv.org/abs/2602.14878)). Tool Use Examples raised complex-parameter accuracy from 72% to 90% ([Anthropic, 2025-11](https://www.anthropic.com/engineering/advanced-tool-use)), but OpenAI warns examples "may hurt performance for reasoning models". Run them as experiments.
- **Tool search: better than loading everything, worse than knowing** — Opus 4 went from 49% to 74% with tool search on a large library (Anthropic); it is not worth it under ~10 tools ([Agent SDK docs](https://code.claude.com/docs/en/agent-sdk/tool-search)). Failure modes are documented: exact-name ranking misses in Claude Code and Codex, stale indexes, wasted lookups. Routing in the harness (embedding pre-selection: 94.5% coverage against 69.0% for a static list) beat search driven by the model. No source compares tool search with a tool-listing skill. Partly contradicts overview 6.3.
- **Code execution wins on data, not everywhere** — Anthropic's Programmatic Tool Calling: −37% tokens and small accuracy gains; Cloudflare fits 2,594 endpoints in ~1,000 tokens ([Cloudflare, 2026-02](https://blog.cloudflare.com/code-mode-mcp/)). Independent tests: on a 10,000-row aggregation, direct calls got 2/10 right against 10/10 for code ([Gatana, 2026-10](https://www.gatana.ai/blog/code-mode-vs-direct-tool-calls-benchmark)). But direct tools beat code on a clean 10-tool API (0.995 against 0.97, [npow](http://npow.github.io/posts/mcp-beats-code-generation/)), and Gemini models fell from ~2/3 to ~1/3 pass rate under code mode ([IJCA 2026](https://www.ijcaonline.org/archives/volume187/number136/mbat-ijca-2026-e10508249e55.pdf)). Inference: a Kiln code-tool wrapper is code mode done when the tool is written, which suits recurring agents.
- **SQL and GraphQL** — curated views or a semantic layer first; then column descriptions, sample values, a glossary and verified example queries, retrieved per question. Guard rails go in the database and in code, never only in the prompt. Cap rows and signal truncation; set cost limits (`EXPLAIN`, GraphQL demand control). OpenAI's data agent adds memory of corrections and meaning taken from pipeline code ([OpenAI, 2026-01](https://openai.com/index/inside-our-in-house-data-agent/)). Confirms the overview's "sample queries over schemas". No published timestamp checklist exists, so that section would be original.
- **Wrappers over fixed enterprise APIs are a named pattern** — "agentic overlays" ([AWS, 2026-06](https://aws.amazon.com/blogs/machine-learning/retrofit-dont-rebuild-agentic-overlays-for-transforming-legacy-enterprise-services/)) and the "Agent Tool Facade" ([2026-10](https://sol4biz.at/the-agent-tool-facade/)). They add points the overview misses: identity bound from the session, not the model; canonical error mapping; rate limits; read / qualify / draft tiers for writes. None measures a wrapper against the raw API on an eval.
- **Keep the tool list stable for the cache** — adding or removing tools mid-loop breaks the KV cache and confuses the model ([Manus, 2025-07](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus)). Relevant to the overview's caching argument (6.2).

## Against the baseline (project overview)

- **Confirms**: API ≠ agent tool (6.3); the three example failures (huge list results, chains, general SQL/GraphQL that needs schema knowledge); wrap, do not rewrite; roll-up tool plus "call it first" (7.5); huge tool results as a blocking red flag (9); sample queries over schemas, with the schema as leaf nodes (10); long tool descriptions as a red flag (9).
- **Contradicts or qualifies**: "a side skill … is almost always better" than tool search — no comparison supports it, and tool search wins against loading a large catalog. Code execution and wrappers do not always help; small clean tool sets and some models do better with direct tools.
- **Missing**: tool count and overlap as a smell; tool *removal* and scoping as experiments; error-message design; opaque ids; a verbosity enum; parameter design (enums, flat schemas, no arguments the harness already knows); tool-use examples; return-shape docs; namespacing as an experiment; tool routing in the harness; stable tool lists for caching; the step cost of description rewrites; write-safety and identity binding in wrappers; memory of corrections and pipeline code for data agents.
- Already in the repo (not from the web): the build agent's `kiln-harness-tuner-code-tool-authoring` skill ships wrapper templates for pagination, batching, input normalisation, actionable errors, preview and cap, composite resolve-fetch, and a read-only guard. The gap is mostly the map from smell to experiment, not the mechanics.

## Open Questions / Gaps

- No study compares a progressive-disclosure skill that lists tools with tool search or with direct loading. The overview's claim is untested.
- No published measurement of a wrapper layer against the raw enterprise API on an agent eval. The evidence comes from consolidation case studies and code-mode benchmarks.
- Block's "measured improvements" for its Linear server: we could not find the numbers at the source.
- Composio's schema-flattening result is from 2024 models; we found no 2026 replication.
- We found no checklist for timestamps in query tools.
- We found no comparison of "truncate with notice" against "refuse and ask for a narrower query" for oversized results.
- Most independent code-mode and tool-count studies are small (5–30 tasks) or run by vendors. Treat their numbers as directional.
- Not confirmed whether Kiln run configs can defer tools, scope tools, or let the subject agent run code the model writes at run time. This belongs to the Kiln-gap subtopic.
- Tavily extract was rate-limited (HTTP 429) for most of the session; Exa was used instead. No source was dropped because of it.
